The CPU is m9b's VexiiRiscv, configured the same way, with the same caches and the same 24-bit address trick ([m9b part 2](/m9b/cpu/) has all of that). Three things are new: a floating-point unit, two thirds again the clock, and memory behind it that behaves differently. Getting there was mostly a hunt for faults that only appeared on the board, never in simulation.
{: .lede}

## A floating-point unit

Quake does all its geometry in floats. Without hardware floats, every `fadd` and `fmul` is a call into libgcc's soft-float routines, dozens of instructions each. VexiiRiscv can generate the F extension (single precision) with one more option, and on the 20K there finally was room for it:

```
--with-rvf --fma-reduced-accuracy
```

<div class="table-wrap" markdown="1">

| | Without the FPU | With it |
|---|--:|--:|
| Logic | 37% of the chip | 55% |
| Block RAM | 27 of 46 | 30 (the float register file) |
| Multipliers | | 4 more DSP blocks |
| CPU Fmax | | 58–66 MHz depending on the layout, against 60 needed |

</div>

That's about 3,700 logic cells, almost as much as m9b's whole CPU. `--fma-reduced-accuracy` lets the fused multiply-add round twice, as an ordinary multiply then add would, which saves a wide adder and doesn't matter to any game.

Two lessons came with it:

- **Subnormals must survive loads and stores.** The first build used `--fpu-ignore-subnormal`, which flushes tiny values to zero. Fine for arithmetic, but it also flushed them in `flw` and `fsw`, which are supposed to move bits unchanged. QuakeC keeps integers (entity numbers, function indices) in float fields, and as floats those bit patterns are subnormals: Quake died at once with "prog stack underflow". Keeping subnormals cost about 600 cells.
- **The F extension is single precision only.** Doubles are still software. Quake uses `double` in places where it doesn't need it, and calls `sin`, `sqrt`, `floor` on floats via their double versions. Mapping those to float versions and turning the hot renderer's `double` locals into `float` took Quake from 6.4 to 9.3 fps, before any other optimization ([part 4](../games/)).

The runtime needed two small things too: picolibc's start-up leaves the FPU off (`mstatus.FS`), so the first float instruction trapped until a constructor turned it on, and the trap handler now emulates misaligned `flw` and `fsw` along with the integer loads and stores.

## 54 MHz, then 60

On m9b the CPU ran at half the memory controller's clock, synchronously, so the bridge between them needs no slow synchronizers. m20 keeps that: 108 MHz for the SDRAM, 54 for the CPU. The CPU closes timing at about 63 MHz, so the obvious next step was 60/120, and it got a long try.

At 60/120 the board booted, the memory tests passed, and Quake ran its timedemos. But Quake's timedemo plays back a recording, and real-time interpolation means a slightly different machine renders slightly different frames: "it finished" says little. So I made it deterministic, with fixed time steps and a fixed random sequence, and a hash of every frame, comparable between builds, clocks and boards.

<div class="table-wrap" markdown="1">

| Clocks | Wrong frames per run | Notes |
|---|---|---|
| 54/108 MHz | 0, on both boards, every run | |
| 60/120 MHz | 0–2 idle; 94–203 under extra memory load | always in the 3D view, never in the status bar; more on one board than the other |
| 57/114 MHz | crashes within the first 500 frames | three different layouts, both boards |

</div>

Memory patterns, arithmetic tables and instruction fetch checks, all running alongside the game, stayed clean at 60 MHz. Whatever goes wrong is outside what they cover, and the difference between boards points at physical margin, unproven. So 54 MHz it was, for a while, with the frame hashes as the test for the next attempt.

### 60 MHz after all

The next attempt found three things. First, the SDRAM's reads (next section): caught on the rising edge alone, they sat about 1 ns from the early end of their window, and a warm board now and then lost single bits of fetched instructions. Reads went back through IODELAYs into IDDRs, and the boot ROM now sweeps the capture cycle, edge and delay and keeps the middle of the longest passing run. That fixed the traps, not the wrong frames.

Second, the wrong frames followed the layout, not the clock or the timing report. The same RTL placed differently was clean, or drew a hundred wrong frames, or trapped at the same instruction every run, and layouts with more reported margin were often worse. One failing layout was clean at 57 MHz and failed at 58.5, with nothing changed but the PLL; its trap bit was the slowest bit of a ten-level load-to-use bypass path routed right across the die. On long routes the silicon seems to be about 12% slower than Gowin's model says.

Third, a layout that works can be found, but each change of the design needs a new search: a few overconstraint and placement variants, the ones that meet timing hash-tested twice on both boards, then a moving game for ten minutes or more. The first layout to pass went into the boards' flash in mid-November; the span engine's stride mode ([part 3](../span-engine/)) found no passing layout in four tries until the engine was trimmed to make room. 60/120 has been the mainline since, with no margin to speak of: the current layout traps at 61.5 MHz and doesn't start at 63.

## SDRAM: from clever to simple

The memory side changed completely, from two HyperRAM dies on a DDR bus to one 32-bit SDRAM, and the controller went through a few versions before it got simple.

The first was conventional: the SDRAM's clock from a PLL output with an adjustable phase, swept by the boot ROM to find a working window (8 of 16 phases at 108 MHz). Then reads moved to IODELAY lines and falling-edge capture, when the phase window looked like the limit for 120 MHz. Then a bare test design, with one clock for both the controller and the SDRAM's clock pin, no phase shift and no delays, turned out to work up to 162 MHz with bursts alone. In the SoC it just worked: the routing delay of the clock pin gives writes their margin, and reads only needed the right number of whole cycles, which the boot ROM picked from four. That turned out to leave too little margin on warm boards (above): reads now go through IODELAY into IDDR after all, both in the pin's I/O cell, and the boot ROM centres the capture in a window of about 7 ns at 120 MHz.

<div class="table-wrap" markdown="1">

| | |
|---|---|
| Transfers | ACTIVE, then 8-word bursts back to back, the last with auto-precharge: no row is ever left open, so there's nothing to track, and a refresh fits between any two transfers |
| A cache line | 2 bursts (64 bytes) |
| A DMA block | 8 bursts (256 bytes), one at a time so cache lines get in between |
| Clients | refresh, then the CPU's cache lines, then the span engine, then video and audio DMA |
| Boot benchmark | read 92 MB/s, fill 72 MB/s, copy 24 MB/s (through the caches, 128 KB each) |

</div>

A 162 MHz attempt (3:1 to the CPU) closed timing but had a 3-in-16 phase window, and would have gained 0 to 4%: a cache miss waits mostly on the SDRAM's fixed timings, not on its clock.

## Two faults the simulator never saw

Everything above passed simulation. These two didn't show up there at all. They only appeared on the board, intermittently, depending on how the tools happened to place the design. Each looked for a while like a timing problem, a power problem, a bad chip, or a software bug.

### Reading and writing the same block RAM address

Some bitstreams were simply bad: traps at instructions that can't trap, `fsqrt` returning wrong results, an instruction word fetched one bit off from what was in memory. The same logic placed differently was fine. Half the clock made no difference, a second board made no difference.

Gowin's documentation (UG285) has one line on it: *performing read and write operations to the same address at the same time is not allowed*. SpinalHDL's memories assume read-first behaviour, the simulation model agrees, and VexiiRiscv relies on it all the time. A pipeline halt doesn't stop a block RAM read, so every instruction cache miss reads the very word its refill is writing. On this chip, that read can disturb the stored bits, and how much depends on the layout.

The fix is a script run on the generated Verilog: every block RAM write goes through a one-entry pending register, and a read of that address takes the register instead of the RAM. The logic sees exactly the same values, cycle for cycle, and the two ports never meet. The register files moved to LUT RAM, which has no such rule (and freed 5 block RAMs). A simulation probe counts collisions: zero since. The reproducer was a small loop of integer code with an `fsqrt` in flight: 3,000 failures in 3,000 runs on one layout, none on others, and none on any layout after the fix.

### The word-write bypass

m9b's data cache writes whole 32-bit words, because the 9K's block RAM byte enables misbehave: a byte store reads its word, merges its byte in, and writes the word back, an option I added to the fork. On the 20K, the same CPU crashed a live Quake within minutes, with bad surface indices in its edge lists, but never in a timedemo, and in no simulation.

Removing options one at a time found it: without word writes, the crashes stopped. Later the cause became clear. A younger access in the same cycle took the word's other bytes from the RAM while it was being written, and on this chip a read-during-write collision doesn't return the old data. The fork's bypass now carries the whole merged word, so nothing reads the RAM mid-write, and word writes are back: 4 of 4 five-minute runs clean, where the previous version trapped in 4 of 4. (Without word writes it's stable too, at six more block RAMs.)

### And one that wasn't the CPU

The span engine's request to the SDRAM controller crossed into the controller's clock domain unsynchronized, in the same clock as its address. On some layouts that sent a write to the wrong cache line at 54 MHz, and was fine at half the clock. One flop fixed it. The worst layouts went from 0 of 6 clean runs to 5 of 5.

## Resyncing with upstream

The fork the CPU is generated from had fallen 61 commits behind upstream VexiiRiscv. Before the faults above were found, the old base crashed a live game within minutes in ways that never showed in simulation: faults next to floating-point instructions, at places that can't fault. Sound, the span engine, SDRAM and instruction refills were each ruled out with soak tests, and a soft-float build ran clean for 25 minutes. Rebased on upstream, the same Quake binary ran 31 minutes without a fault. Which upstream commit made the difference isn't known.

## Lessons for intermittent faults

These ate more time than everything else in the CPU put together. What helped:

- **A clean run proves little.** One crash-prone build ran clean 2 times in 7. Count several runs, and compare binaries with `cmp` before trusting an A/B: two "different" builds once differed only in a timestamp.
- **Make the test deterministic.** The frame-hash timedemo turned "it seems fine" into a number per frame, comparable across clocks and boards.
- **Remove one option at a time** on a build that crashes, rather than reasoning about which one it could be.
- **Suspect software too.** A Quake freeze that came and went with bitstreams turned out to be a NaN in Quake's own edge setup: different timing just picked different camera positions.
- **Test every bitstream on the board**, on two boards if possible, with a live game rather than a benchmark: some of these faults never appeared in a timedemo at all.
